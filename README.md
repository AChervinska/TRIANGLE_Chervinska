# Рефакторинг проєкту Triangle
## Зауваження до коду

1. **Немає перевірки на від'ємні сторони.** Конструктор приймає, наприклад, `(-1, 2, 2)`, хоча довжина сторони не може бути від'ємною.
2. **Можна передати нульову сторону.** Значення `0` не відхиляється, хоча такий трикутник не є звичайним невиродженим трикутником.
3. **Не перевіряється нерівність трикутника.** Наприклад, сторони `(1, 2, 4)` приймаються без помилки.
4. **Не відхиляється вироджений трикутник.** Для `(1, 2, 3)` сума двох сторін дорівнює третій, але об'єкт усе одно створюється.
5. **Не перевіряється `Double.NaN`.** Таке значення можна передати замість довжини сторони, після чого обчислення стають некоректними.
6. **Не перевіряються нескінченні значення.** Конструктор допускає `Double.POSITIVE_INFINITY` і `Double.NEGATIVE_INFINITY`.
7. **Порожній конструктор створює об'єкт зі сторонами `0, 0, 0`.** Такий об'єкт не відповідає визначенню трикутника.
8. **Сетери `putA()`, `putB()`, `putC()` не перевіряють значення.** Навіть якщо трикутник спочатку правильний, його можна зіпсувати після створення.
9. **Сторони можна змінювати в будь-який момент.** Це ускладнює контроль правильності стану об'єкта; для цієї задачі зручніше зробити клас незмінюваним.
10. **Назви гетерів `takeA()`, `takeB()`, `takeC()` нестандартні.** Зазвичай у Java для таких методів використовують `getA()`, `getB()`, `getC()`.
11. **Назви сетерів `putA()`, `putB()`, `putC()` теж нестандартні.** Вони не відповідають поширеній домовленості `set...`; після переходу до незмінюваного класу ці методи взагалі не потрібні.
12. **Назва `perim()` не дуже зрозуміла.** `getPerimeter()` краще показує призначення методу.
13. **Назва `area()` відрізняється від стилю інших методів доступу до результатів.** Я замінила її на `getArea()` для послідовності.
14. **Назва `equilateral()` не показує, що метод повертає `boolean`.** `isEquilateral()` читається зрозуміліше.
15. **У `area()` периметр обчислюється кілька разів.** Виклик `perim()` повторюється чотири рази в одному виразі, хоча повторення можна прибрати.
16. **Формула площі не захищена від неправильних сторін.** Через відсутність валідації вираз під коренем може бути від'ємним і результатом стане `NaN`.
17. **Формула Герона в початковому вигляді може втрачати точність.** Особливо це помітно для дуже витягнутих трикутників; можна використати чисельно стійкіше переставлення формули.
18. **Метод `equilateral()` містить зайвий `if/else`.** Результат логічного виразу можна повернути одразу.
19. **Метод `equals()` використовує `instanceof Triangle triangle`.** Цей синтаксис не компілюється на старіших версіях Java, зокрема Java 8 і 11.
20. **У початковому проєкті немає перевірок граничних і неправильних значень.** Без тестів важко помітити помилки після змін у класі.




- Додала перевірку сторін у конструкторі: вони повинні бути додатними, скінченними та задовольняти строгу нерівність трикутника.
- Зробила поля `a`, `b`, `c` приватними та `final`, прибрала сетери й порожній конструктор. Тепер після створення об'єкта сторони не змінюються.
- Перейменувала методи на `getA()`, `getB()`, `getC()`, `getPerimeter()`, `getArea()`, `isEquilateral()`.
- Додала `isIsosceles()` для перевірки рівнобедреного та `isScalene()` для різностороннього трикутника.
- Замінила формулу площі на переставлений варіант формули Герона, який краще поводиться для деяких складних значень.
- Спростила перевірку рівностороннього трикутника.
- Переписала `equals()` без нового синтаксису `instanceof`, щоб код працював і на Java 8.
- Залишила порівняння сторін у тому самому порядку, що й у вихідному класі: `(3, 4, 5)` та `(4, 3, 5)` вважаються різними об'єктами за `equals()`.
- Додала в `Main.java` приклад використання класу й 21 перевірку, які запускаються окремим аргументом `--test`.
